# Runtime lifecycle

This is the Step 4 ownership/reset model. It describes in-memory lifetime only; it does not expand or decide the save schema.

| System | Category | Current creator / singleton / persistent | Owned state | Scene references | Reset, unload and rebind policy |
|---|---|---|---|---|---|
| `GameManager` + `GamePersistenceHost` | A service containing B run state | First gameplay `PaperBattle` instance; singleton; authoritative object detaches to a root and uses `DontDestroyOnLoad` | Combat level, encounter kills/boss/death flags, gameplay initialization count; hosts progression/meta components | `LevelGenerator`, `ZoneManager`, `LootManager`, `DeathMenuUI` | Clear on gameplay unload; resolve only inside the newly loaded gameplay scene. Every gameplay entry resets run-local containers, starts level 1, then consumes/restores one requested load. A duplicate destroys itself before detaching/subscribing. |
| `Inventory` | B run state | First gameplay prefab; singleton; persistent root | Gear list and pickup filters | None; owned `Gear` GameObjects are parented beneath this persistent root | Inventory gear is destroyed/cleared on every gameplay entry before optional load. Ancient currency is retained until its New Game meta policy is decided. `Changed` subscribers are instance-scoped; `GearChanged` subscribers must unsubscribe on disable. |
| `EquipmentManager` | B run state with scene adapter | First gameplay prefab; singleton; persistent root | Equipped Gear dictionary | Current gameplay `PlayerController` and `StatsComponent` | Clear bindings on gameplay unload/Main Menu; bind by exact gameplay scene on load and reapply retained equipment once. ## Transition contracts

- **Cold Main Menu:** no persistent service set is created. The first gameplay scene creates it. Main Menu UI and its dormant popup are scene-lifetime.
- **New Game:** `RequestNewGame` first clears stale load intent. Gameplay entry clears equipment/inventory/ordinary currency/armed crafting intent/rebirth confirmation, resets XP/passives and encounter state, binds the new gameplay objects, starts level 1/stage 1, and lets the new player create one starter weapon. The action does not delete or directly overwrite a save. It does not clear relic history or Ancient currency in this step; those meta rules and later save/autosave policy are deferred.
- **Load Game:** normal fresh initialization happens once, the one-shot request is consumed once, and the existing V1 `GamePersistence.Load` replaces the currently supported inventory/equipment/currency/relic fields. No schema fields were added.
- **Restart after death:** this remains a current-combat-level restart. It resets encounter kills, boss/death flags, enemy/player encounter resources and spawns a normal enemy while preserving combat level, XP/passives, inventory, equipment, currencies, relics and selected skill.
- **Return to Main Menu:** the gameplay scene destroys combat, actors, pickups and HUD. Persistent managers remain exactly once, but their player/zone/loot/death-menu/stat references are cleared. Save data is not deleted. A later New Game or Load Game binds only objects from the new gameplay scene.

## Static and event policy

`GamePersistence.loadRequested` is mutable static transition intent and is cleared by New Game or one consume. Singleton `Instance` fields represent their documented category and clear only when the authoritative owner is destroyed; duplicate owners never replace them. `BattleManager.InstanceChanged` and `CurrencyInventory.GearChanged` are static events: scene subscribers pair subscribe/unsubscribe in enable/disable or destroy paths. `GameManager` and `EquipmentManager` each subscribe once to `SceneManager` only after winning singleton authority and unsubscribe on genuine destruction. UI open flags clear on scene UI destruction. Read-only roll tables, regexes, and art/audio/sprite caches are application caches and intentionally survive scene transitions.
